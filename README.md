# firmware-stopwatch 固件码表

**设备反应慢，到底慢在哪一步？**

## 报告长什么样

下面是小智（M5Stack CoreS3）的 10 轮实测数据，按 v0.4.1 界面和规则重新生成的报告。

![报告：结论建议](docs/示例/报告-结论.png)

完整报告（10 轮）：[docs/示例/小智-说完话到开口.html](docs/示例/小智-说完话到开口.html)（下载后用浏览器打开）

固件码表读一份单片机固件的源码，用大模型找出关键步骤，在这些位置插入计时点（只打印时间戳，不改业务逻辑），编译、烧录后让设备真实运行多轮，最后生成分段用时报告：哪一步慢、为什么、怎么改。研发来跑，不写代码的负责人也能看懂结论。

## 跟其他测法比

研发测延时，常用打印时间戳、逻辑分析仪或 ESP-IDF 自带的追踪工具。码表跟它们比，好在四点：

1. **不用先知道该在哪测。** 别的办法都要研发自己想好在哪打点、夹哪根线。码表让大模型读源码，自己找出关键步骤、自动插好计时点，测完一键还原。
2. **测的是用户真正在等的那段时间。** 比如"说完话到设备开口"，中间要经过设备、网络、服务器。逻辑分析仪只看得到引脚，追踪工具只看得到芯片内部，拼不出这一整段。
3. **直接告诉你哪段慢、怎么改。** 别的工具给的是一堆数字或波形，还得自己看。码表对照有出处的体验标准（比如智能音箱团体标准 T/CESA 1045-2019：说完话到开始回答平均不超过 2 秒）判快慢，写清原因和改法，负责人和研发各一版。
4. **改完能说清是不是真变快了。** 测多轮取中位数，算出正常波动，告诉你这次是真快了，还是误差。

**短处也说清楚**：

- 计时点要经调试口打印，本身有一点开销，适合看几十毫秒以上的段；抠微秒级时序、看引脚电平请用逻辑分析仪。
- 要用大模型，需要自己的密钥或本机已登录的 Claude Code。
- 目前只支持乐鑫 ESP-IDF，只在小智一个固件上真机实测过（见下面"当前状态"）。

## 目标

- **测 → 判 → 改 → 验 闭环**：测出每段用时；按体验标准判人等不等得了，第二次起再看比上次快了还是慢了；指出最慢且能改的那段并给出修改建议；改完再测，前后对比证明变快了。
- **一份报告，两种读法**：给负责人的是结论和可选方案，给研发的是代码位置和具体改法。
- **通用**：码表事先不知道被测固件是做什么的，语音对话、门禁刷卡、按键、传感器等由事件触发的流程都按同一套方法测。只要求固件能从源码编译、能通过 USB 调试口输出日志。
- **平台路线**：乐鑫 ESP-IDF → STM32 → 树莓派 Pico。
- **不做**：全面代码审查、自动修改业务代码、监听设备间通信总线（如 485）、测量机械动作时间。

## 当前状态（v0.4.1）

第一版已完成并通过真机验收，但**只在一个固件上实测过**，请把它当作早期版本使用。

**v0.4.1 更新**：码表对 DeepSeek 的支持尚不完善，正在修复，因此暂时隐藏设置页入口。请使用 Claude API 或本机已登录的 Claude Code。此前保存过 DeepSeek 的用户，请在设置中改选 Claude 并保存；原密钥文件保留。本次仅调整模型入口及提示，不包含其他流程或设备控制修复。

| 项目 | 状态 |
| --- | --- |
| 被测固件 | 只实测过开源项目 [xiaozhi-esp32](https://github.com/78/xiaozhi-esp32)（小智 AI 语音对话），板子是 M5Stack CoreS3（ESP32-S3），ESP-IDF v6.1 |
| 已跑通的流程 | 选择源码 → 点「开始测量」后一页走到底：大模型识别关键步骤 → 插入计时点 → 编译烧录 → 试一次 → 10 轮实测 → 分段用时报告与修改建议；导出报告、测完自动还原原版固件；改完代码一键再测，报告和上次比 |
| 判慢 | 第一次测按体验标准判"人等得了吗"（语音对话、屏幕反馈等 7 类设备各有带出处的标准，对不上的用尼尔森 0.1/1/10 秒三档；只有标准给了"好"的档才分 差/可以/好 三档，只有及格线的照旧两档（写"达到及格线"））；第二次起再加"比上次快了还是慢了"。看达标率（没超过体验标准的轮次占几成）；某轮特别慢不剔除，照样算进达标率。结论标签：出错（功能坏了，如回答开头被吞）、必须改（达标率 < 50%，或超过标准 1.5 倍的轮次 > 10%）、建议改（达标率 < 90%，或比上次慢了：差要同时大于 0.1 秒和 10%）、未判（没有体验标准、也没有上次可比，只记用时）；没问题的线不列 |
| 改完再测 | 计时点那几处代码没动，就沿用上次的关键步骤和插法，不调用大模型；报告写和上次比快了、慢了，还是在正常波动内。实测过把小智升级到上游新版（17 个提交） |
| 自动测试 | 770 个，覆盖语音对话、门禁刷卡等模拟场景 |
| 操作系统 | 苹果芯片的 Mac 实测通过；Windows 还没有实测 |
| 大模型 | Claude API、本机已登录的 Claude Code；DeepSeek 入口暂时隐藏 |

其他乐鑫固件理论上可以走通同样的流程，但还没有验证，识别结果可能需要较多人工确认。非语音设备（如门禁刷卡）只用开源项目走过识别关键步骤，还没有真机测过 10 轮。

**下一步**：拆开看服务器和固件各占多少时间；补 Windows 实测和 STM32 支持。

## 在 Mac 上安装

需要苹果芯片的 Mac，并且已经装了 [Homebrew](https://brew.sh)。

1. 装 uv（Python 的安装工具，它会自动准备好合适版本的 Python，不动系统自带的 Python）：

   ```sh
   brew install uv
   ```

2. 拿到代码（也可以在 Releases 页面下载压缩包解开）：

   ```sh
   git clone https://github.com/seagartech/firmware-stopwatch.git
   cd firmware-stopwatch
   ```

3. 启动。第一次会自动装好需要的东西，要等几秒：

   ```sh
   uv run fsw --version
   ```

   看到 `firmware-stopwatch 0.4.1` 就是装好了。再运行 `uv run fsw`，码表会在浏览器里打开本机网页（地址是 http://127.0.0.1:8765），并告诉你还有哪些设置没填。关掉窗口或按 Ctrl+C 就停止。

## 怎么用

1. 运行 `uv run fsw`，浏览器打开码表首页。
2. 选被测固件的源码文件夹和板子，首页显示预计总耗时。
3. 点「开始测量」。之后在同一页自动往下走：识别关键步骤 → 插入计时点 → 编译烧录 → 试一次 → 10 轮实测 → 出报告。中途随时可以停止。
4. 需要人工操作时（比如对设备说一句话、刷一次卡），页面大字提示并响一声，照做即可；自动检查发现问题才会停下来请你处理。
5. 测完自动出报告并存下来，首页「以前测过的」里能再打开、导出；测完可以一键还原成原版固件。
6. 改了代码以后，在「以前测过的」里点「改完了，再测一次」，报告会写和上次比快了还是慢了。

## 设置和密钥

设置放在你自己电脑上，不在代码文件夹里：

- Mac：`~/.config/firmware-stopwatch/`
- Windows：`%USERPROFILE%\.config\firmware-stopwatch\`

把代码里的 `config.example.toml` 复制到这个文件夹，改名为 `config.toml`，照里面的说明填。以后也可以在码表网页的设置页里改。

密钥不写进 `config.toml`，单独放一个文件，只写密钥本身一行：

- Claude：`claude_key.txt`
- DeepSeek：`deepseek_key.txt`（仅说明已有配置；入口暂时隐藏，当前请使用 Claude）

也可以用环境变量 `ANTHROPIC_API_KEY`、`DEEPSEEK_API_KEY`，环境变量优先。选"本机已登录的 Claude Code"时不用密钥。
